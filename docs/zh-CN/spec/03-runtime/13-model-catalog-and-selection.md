# 13. 模型目录及选择

> **翻译说明：** 本页是与 [英文源规格](/spec/03-runtime/13-model-catalog-and-selection) 一一对应的机器辅助翻译。代码、协议字段和标识符保持原文；如翻译与英文源事实有歧义，以英文版本为准。


## 1. 产品规则

用户必须能够广泛使用**市场上可用的模型**，而不仅仅是精选的演示子集。

因此：

1.目录可刷新
2. 始终允许自定义模型 ID
3.兼容OpenAI的网关是一流的
4. 搜索是跨启用的提供商的全局搜索

## 2. 选择用户体验

模型配置是**发现优先**的：AI 服务自己才是"它提供哪些模型"的权威，因此先向该
服务自己的端点发问，models.dev 只用来丰富返回的结果。随包目录绝不会被呈现成
一份可浏览的"所有已发布模型"列表——一个部署未必托管了它的厂商发布的全部模型，
一个 key 也未必有权使用它们。

### 设置：单一提供商表单

`ProviderSetupDialog` 是一个单一表单，不是向导：

- **名称**、**Base URL** 和 **API Key** 同时呈现在屏幕上。编辑时把 key 留空
  表示"保留已存的那个"；只有用户确实输入了内容才会发送 `secretValue`。
- 模型区列出服务返回的内容。`useProviderModels` 对编辑做 600 ms 防抖，用一个
  单调递增的请求序号防止乱序响应，并且不需要 API key，因此本地网关和免认证
  网关同样能解析。已保存的提供商会立即画出它的缓存列表，随后用实时结果替换。
- 对该列表的过滤发生在客户端：它是一份简短的实时列表，不是目录，因此不涉及
  任何宿主端搜索。
- 列表标题栏有一个复选框，一步选中或清空当前可见的每一行，这样一份很长的服务
  列表不必逐个勾选。当搜索过滤生效时，"全部"只指匹配的那些行；过滤之外已经
  选中的模型保持选中。新增的行采用 `bindingFromModelInfo`（或自定义模型
  默认值）；已存在的绑定保留它们的高级覆盖。可见行全部选中时该复选框为选中，
  全都未选时为未选，可见集合混合时为不确定态。
- 同一个标题栏上还有一个"获取列表"操作，会立即探测服务，跳过 600 ms 的编辑
  防抖和先画缓存的行为。加载期间现有的行保持可见。凭据编辑触发的自动发现保持
  不变。空闲、加载中或表单正在保存时，该控件不可用。
- 上下文窗口、输出上限与初始思考级别，来自对丰富后记录调用
  `bindingFromModelInfo`；按模型的覆盖放在每一行的 **Advanced** 展开区里。
  `publishedThinkingLevels` 描述的是目录基线，并为已知模型的绑定播种。对话框
  始终提供七个规范级别，未知记录或非推理记录也一样，而运行时使用绑定的显式
  集合。一个既没有发布级别列表、也没有级别映射，但确实声明支持推理的模型，
  仍然会被播种为 `low`/`medium`/`high`。
- 线路 API 由提供商已发布的 `npm` 适配器推导（`apiStyleForAdapter`），并且只能
  在 **Advanced** 里编辑。
- 自定义模型 ID 始终被接受，因此没有 `/models` 路由的网关仍然可用。

### 发现优先级

`providers.listModels` 按这个顺序解析，而且这个顺序是承重的：

1. 解析已存储的密钥，因此一次编辑不需要重新输入 key。
2. `discoverProviderModels` 询问服务（`/models` 或对应风格的等价物）。非空的
   回答获胜，逐个模型经 `modelsDevCatalog.findModel` 丰富，写回模型缓存，并
   以 `source: "remote"` 上报。
3. 只有当端点没有发布任何可用内容时——没有路由、认证错误，或空列表——才由
   `modelsForProvider` 提供该厂商已发布的模型，以 `source: "catalog"` 连同
   任何发现错误一起上报，好让 UI 能说明该服务没有回答。这个结果**不会**被
   缓存，因此一次目录猜测绝不会变得与一次真实探测无从区分。
4. 最后手段：该提供商已配置的模型，`source: "fallback"`。

OAuth 厂商账户跳过第 2 步——它没有可用于探测的 key，而且 pi-ai 已经知道该
订阅允许哪些模型。

选择器绝不会把原始的宿主错误倾泻进模型列表。一次没有任何行的失败探测，会显示
一行经过分类的摘要（认证、缺少列表、限流、超时、网络、无效响应，或 HTTP
状态），外加一句简短提示，建议手动添加 ID。一次仍有缓存行的失败探测会保留
那些行，并把同样的摘要显示为一条紧凑横幅。

### 高级
- "使用自定义模型 ID"
- "刷新目录"
- 按提供商的线路 API 覆盖
- 按模型的上下文窗口、输出上限与思考级别覆盖

## 3. 最新模型

保留最近选择的模型参考：

```ts
type RecentModelRef = {
  providerId: string
  modelId: string
  usedAt: string
}
```

在选择器中显示前 N 个。

## 4. 会话模型绑定

每个会话存储：

- `providerId`
- `modelId`
- `thinkingLevel`（`off|minimal|low|medium|high|xhigh|max`）

在会话中改变模型或思维水平只会影响后续回合。
存储的思维偏好在重启后仍然存在；有效请求级别
在执行时对所选模型进行能力限制。

对于新创建的会话，渲染器会解析所选（或应用默认）模型的 `ModelBinding`。
具有推理能力的模型始于该绑定的 `defaultThinkingLevel`，并钳位到已启用档位；
当默认值未设置时，才回落到已发布 `supportedThinkingLevels` 中的最高已启用档。
非推理模型或缺失的能力元数据从 `off` 开始。这是一个仅创建时的默认值，绝不会
重写现有会话的存储选择。

未固定的会话仍在 list/get/create/fork/configure 上展示该继承默认模型的
推理能力；丰富步骤不会写入 `providerId`/`modelId`。当所选目录/绑定模型
暴露了思考等级时，Composer 不得把 `supportsReasoning: false` 或空等级列表
当作权威快照，因此回合中改档不会把菜单塌缩成只剩关闭思考。

## 5. 能力警告

如果用户在 Agent 模式下选择不带工具标记的模型：

- 显示非阻塞警告
- 不要硬阻止（供应商标签可能不完整）

## 6. 刷新行为

随包的 `apps/desktop/resources/models.dev/api.json` 快照是启动基线。它由
`scripts/release.mjs` 在创建发布标签之前刷新；应用启动既不抓取也不写入目录。
设置通过仅限 Electron 的 `providers.refreshModelCatalog` 通道重新抓取
`https://models.dev/api.json`；成功的响应只替换当前进程内存中的 models.dev
目录，绝不写入用户数据。

提供商的模型加载仍然是 stale-while-revalidate：

1. `source: "cache"` 从 Rust 拥有的 SQLite 中水合已保存提供商的归一化发现行，
   不访问提供商网络。
2. 渲染器可以立即在 Composer 与提供商对话框中显示这些行。
3. `source: "refresh"` 先使用随包/内存中的 models.dev 目录，只为发现
   models.dev 未暴露的 ID 才去探测提供商端点。
4. 成功的提供商发现可以更新 Rust 拥有的归一化缓存；它不能替换匹配的
   models.dev 记录或其元数据。
5. 当发现是部分的或不可用时，已配置的 `ModelBinding` ID 会被保留；
   models.dev 中不存在的 ID 拿到通用元数据。

## 7. 线下行为

如果刷新失败/离线：

- 使用缓存目录
- 绝不清除已经渲染出来的缓存列表，也不闪现一个空的选择器
- 允许自定义模型 ID
- 仍然允许带有已知模型 ID 的提供商
- 当已保存的提供商缓存为空或不完整时，在套用 models.dev 元数据装点之前，
  先追加每一条已配置的模型绑定，这样多模型设置仍然可编辑，按模型的能力状态
  也保持对齐
- 如果在一次离线发布中随包的发布快照缺失或无效，仍让已配置的 ID 保持可见，
  并带上通用的纯文本元数据

```ts
type ModelCatalogItem = {

    "off" | "minimal" | "low" | "medium" | "high" | "xhigh" | "max"

```

## 9. 选择解析顺序

当 UI/search 为选择器请求模型时：

1. 已启用提供商的最近模型
2. 用户自定义模型
3. 匹配 provider/API URL 的 models.dev 记录
4. 面向自定义或账户专属模型的提供商发现/缓存
5. 始终包含"自定义模型 ID"的输入操作

按 `(providerId, modelId)` 去重，优先级为
`user > models.dev > provider-discovered > recent-only`。`catalogSource` 字段
记录一次 models.dev 匹配；提供商缓存只存储归一化的选择字段，并在下一次读取时
由本地的原始目录重新装点。

### 9.1 有效上下文窗口

运行时与上下文检查器使用同一个有效模型窗口。来自 models.dev 的正数已发布
`limit.context` 会替换旧绑定中可能残留的 `128,000` 通用种子；这使得刷新后的
目录记录（例如 `gpt-5.6-luna`，`1,050,000` token）不再表现为一个 128k 模型。
通过按模型的 Advanced 控件填入的非默认值，仍然是用户的显式覆盖。未知模型
依旧使用保守的 128k 通用窗口，绝不会仅凭 ID 模式就被提升。

### 9.2 对话 Composer 范围

对话 Composer 是已配置模型选择器，而不是原始发现目录。对于每个已启用且
可运行的提供商，它只渲染该提供商持久化 `models` 绑定中的模型 ID（或旧版
`defaultModelId` 回退值）。缓存或实时发现的记录可以为这些行补充显示名称和
元数据，但未配置的发现模型不会出现在对话区列表中。发现不可用时，已配置的
模型 ID 仍会单独显示。

设置中的提供商对话框仍使用发现结果添加和配置模型；保存模型绑定后，该模型才
有资格出现在 Composer 中。

## 10. 默认模型策略

应用级默认：
- 第一个成功通过测试的提供商 + 它的 default/recommended 模型
- 设置里的默认模型选择器，按提供商列出每一个已配置的模型；选中某一项会同时
  持久化所属提供商与那个确切的模型 ID
- 该选择器支持跨提供商名称与模型 ID 的本地搜索；结果列表在浮层内滚动，没有
  模型匹配时显示明确的空状态
- 该选择器使用简洁的、设置专用的搜索文案；每条结果在视觉上优先呈现模型 ID，
  提供商则作为次要元数据
- 结果按提供商分组，因此提供商名称每组只出现一次，而不是在每个模型行上重复
- 如果一个都没配置，新手引导清单要求在第一次运行 agent 之前先完成提供商设置

会话级：
- 创建时继承应用默认
- 把思考级别初始化为所继承模型的绑定所启用的最高级别；已发布的级别为新绑定
  播种，而空的或只有 `off` 的绑定从 `off` 起步
- 可以独立覆盖

## 11. 能力门控

| mode/feature | 所需能力 |
|---|---|
| Agent 模式工具 | `tools`（如果丢失则发出警告；仅当运行时无法运行时才硬块） |
| 图像输入 | `vision` |
| 推理 UI 可供性 | `reasoning` |
| 结构化修复助手 | `json` 可选 |

除非不可能执行，否则警告是非阻塞的。

### 11.1 推理能力解析

1. 为匹配的 provider/API URL 与确切的 `modelId` 解析 models.dev 元数据。当
   已配置的提供商使用不带前缀的 ID 时，匹配也接受目录的厂商前缀（例如
   `deepseek-v4` 仅在提供商身份匹配的前提下匹配 `deepseek/deepseek-v4`）。
2. 对于已发布的 `reasoning` 与 `reasoning_options`，models.dev 记录是权威；
   缓存或提供商声称的能力不能取代它。
3. 对于用户的有效选择，该提供商那条确切的 `ModelBinding.thinkingLevels`
   是权威。它可以显式启用一个目录并未发布的规范级别。
4. models.dev 中不存在的自由格式 ID，起初是一个未知的通用模型，只暴露
   `off`；设置只能在一次显式的绑定选择之后提升它，绝不能通过发现或自动推断。
5. Composer 按规范顺序渲染有效的绑定级别。若不存在绑定，则回退到已发布的
   模型级别与提供商默认值。
6. 如果已存储/被请求的级别不可用，就先向上、再向下扫描，选取最近的已启用
   绑定级别。一个没有任何非 `off` 级别的绑定解析为 `off`。
7. 切换到没有启用任何推理级别的 provider/model 时持久化 `off`；不会有未配置
   的级别泄漏进下一次请求。

### 11.2 视觉能力解析

1. 为匹配的确切模型解析 models.dev 的 `modalities.input`。
2. 只有当 models.dev 记录包含 `image` 输入时，才把该模型标记为 `vision`。
3. 提供商端点、缓存或用户定义的能力标志，作为选择元数据仍然有用，但它不能
   把一个未知模型提升到图片传输。因此未知/自定义模型在 Composer 中显示为
   路径回退状态。
4. 主进程把粘贴的图片准备成内容寻址的引用。具备视觉能力的模型会收到处于
   应用侧 20 MiB 内联上限之内的图片作为临时图片块；其他情况则收到一个安全的
   `@path`。

### 11.3 设置里添加模型时的元数据

当设置表单添加一个服务返回的模型时，它的初始上下文窗口、输出上限、能力徽章
与思考默认值，都来自对丰富后记录调用 `bindingFromModelInfo`，因此常见路径
不需要手工输入 token 数。丰富查找的顺序是：

1. 先按 `vendorKey` 优先匹配 models.dev 提供商，其次按归一化的提供商 API URL，
   其中包括显式的原生适配器别名，例如 `openai-codex` → `openai`；由它那条
   确切的模型记录提供这些字段。
2. 提供商端点可以补充自定义/账户专属的 ID，但不能取代 models.dev 元数据。
   自由格式的未命中会拿到 `bindingForCustomModel` 给出的固定通用默认值。
3. 这次查找不会把 API key 发送给 models.dev。运行时的模型解析使用同一条
   models.dev 记录和选定的 pi-ai 传输适配器。

## 12. 刷新策略

- settings/model 选择器中的手动刷新按钮
- 提供商 create/test 成功后的可选刷新
- MVP 中没有激进的背景轮询
- 刷新失败保留以前的缓存并显示非致命错误

Electron 用本地的 models.dev 快照装点缓存的和新返回的模型行。运行时的模型
解析把同一份完整的 models.dev 配置传给选定的 pi-ai 传输适配器。提供商发现
仍然只是一个仅提供 ID 的回退，服务于快照中不存在的自定义/账户专属模型。

## 13. 搜索行为

不存在目录搜索通道。用户可挑选的模型就是他们的服务返回的那些，而那份列表短到
足以在渲染器里过滤：提供商表单用一次朴素的、不区分大小写的子串测试，把输入的
文本与模型 id 和展示名称做匹配。

Composer 选择器同样只搜索**已配置**的模型，匹配模型 id、展示名称、已发布的
family 以及提供商名称（`composerModelMatchesQuery`）。

凡是拿被选中的模型去和返回的模型做匹配的地方，模型 id 都按不区分大小写比较，
因此手输的 `GPT-5` 与已发布的 `gpt-5`，对勾选标记、开关和重复项守卫来说是
同一个模型。

## 14. 验收标准

- [ ] 用户挑选模型时看到的列表，就是他们的服务返回的那一份；随包目录绝不
      被当作一份"所有已发布模型"的可浏览列表提供
- [ ] 只有在端点没有发布任何可用内容时才查阅目录，且该结果以 `catalog`
      上报、不被缓存，并携带发现错误
- [ ] 添加一个 AI 服务只需一个表单，没有需要逐步走过的阶段，线路 API 由已发布
      的适配器推导而不是反过来问用户
- [ ] 添加一个被发现的模型不需要手工输入上下文窗口或输出 token；覆盖项留在
      按模型的 Advanced 展开区里
- [ ] API key 路径与 OAuth 厂商账户路径使用同一份实时模型列表和同一种绑定形态
- [ ] 尚未保存的提供商可以直接从表单发起探测，而已保存的提供商复用它存储的
      密钥、无需重新输入 key
- [ ] 自定义模型 ID 路径无需命中目录即可工作
- [ ] 最近使用的模型出现在选择器中
- [ ] 刷新合并进缓存与选择器（绝不做破坏性替换）
- [ ] 重启会在实时刷新之前水合先前的目录，离线刷新让缓存的选择器保持有内容
- [ ] 能力徽章可见
- [ ] 会话模型变更只作用于下一个回合
- [ ] 新会话把具备推理能力的继承模型默认为该绑定存储的默认思考级别
      （钳制到已启用集合上；只有未设置时才取已启用中最强的那个），否则默认
      为 `off`
- [ ] 设置里的选择器始终暴露规范的思考级别阶梯；已发布的级别为已知模型播种，
      而显式的绑定级别在 Composer、Electron main 与 pi sidecar 中以同样的方式
      被钳制
- [ ] 对于匹配的 provider/model，models.dev 元数据获胜；其中不存在的 ID 使用
      通用形态，而 pi-ai 只提供传输/OAuth
- [ ] 提供商设置与缓存的发现结果不能替换已知的目录能力；显式的绑定编辑仍然
      是被持久化的配置
- [ ] 未知的自由格式模型在不臆造能力的前提下仍然可运行
- [ ] 一条 models.dev 记录与一条未知的通用记录，通过同一个选定的传输解析，
      且不会把提供商凭据发送给远端目录
